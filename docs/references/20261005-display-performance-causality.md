# 虚拟显示器与 ColorSync 卡顿：独立对照记录

日期：2026-10-05。环境：macOS 26.5.1 / arm64，内置屏与 LG 外接屏。用户授权独立 demo 热插拔并接受现有会话暂停。没有接管或关闭主 runtime，没有修改色彩配置、物理显示偏好或重启系统服务。

## 目前能确认的前因后果

早期 holder (`128117b`) 每次生成随机 serial；后续 `4b4ef3a` 使用 namespace 哈希槽位，`912ce3f` 收敛为跨 namespace 固定 32 槽。旧 `experiments/VirtualDisplay/Runner/main.swift` 的 `--holder-only` 路径仍使用随机 serial，不能拿它默认 20 次循环来做无界压力复现。本次独立 demo 使用固定池三个槽位，只做四次创建。

**身份变化造成 ICC 持久增长已经实测；ICC 增长造成最早卡顿的完整因果链仍未证明。** 当前系统在 demo 开始前就存在 ColorSync 循环，因此不是从健康系统诱发首次故障的实验。

1. 初始发现 142 个内容/名称与 OCU 匹配的 ICC 文件，约 472 KiB。它们是系统持久文件，并非在线显示器或 helper 数量。WindowServer 布局历史的 UUID 数混有物理设备，不能全部归因于 OCU。
2. 接入固定槽位 A 后文件数 142→143；移除后仍为 143。同 serial 重建，display ID 改变但 UUID 相同，文件数仍 143，已有 ICC 内容哈希未变化。
3. 分别改用槽位 B、C 后变为 144、145；退出后保留。三次身份变化都验证了新增文件，四次退出都确认自身显示器消失。物理屏身份、主屏及坐标在这些创建前后没有变化；这不意味着 Dock 或输入完全不受重配置影响。
4. 没有 OCU 虚拟屏在线时，ColorSync 仍周期处理内置屏和 LG 的 profile。虚拟屏接入后，日志变为三块屏一起反复处理；移除后回到两块屏，但循环仍持续。因此“还有活着的 OCU 虚拟屏或 holder”不是该循环持续的必要条件。

## 热插拔/捕获对照

CPU 为累计 CPU 时间差除以墙钟时间，100% 表示一个核。每窗约 20 秒；捕获包含启动/停止时间，原始精确窗口和样本见脱敏 JSON。调用/s 统计日志处理事件，不是文件写入频率。

| 阶段 | WindowServer CPU | displayservices CPU | colorsyncd CPU | profile 调用/s |
| --- | ---: | ---: | ---: | ---: |
| 两块物理屏，初始基线 | 38.8% | 31.7% | 21.1% | 14.24 |
| A 首次接入，只持有 | 48.3% | 53.1% | 65.7% | 22.94 |
| A，SCK 捕获 | 43.4% | 48.1% | 30.7% | 22.75 |
| 停捕获，A 仍在线 | 49.6% | 52.4% | 35.0% | 22.88 |
| A，捕获 + Metal 渲染 | 44.2% | 48.5% | 32.5% | 22.27 |
| 停渲染，A 仍在线 | 40.2% | 50.2% | 33.6% | 22.95 |
| A 移除 | 29.8% | 30.7% | 18.9% | 15.44 |
| A 同身份重建，只持有 | 44.1% | 55.4% | 37.5% | 24.68 |
| A 再移除 | 37.5% | 35.5% | 23.0% | 16.44 |
| B 接入，只持有 | 37.9% | 54.1% | 58.8% | 26.58 |
| B 移除 | 34.5% | 37.4% | 24.2% | 17.38 |
| C 接入，只持有 | 28.4% | 57.5% | 58.6% | 28.85 |
| C 移除 | 27.4% | 38.0% | 23.4% | 18.82 |
| 全部移除后，额外观察 60 秒 | 26.3% | 37.3% | 22.8% | 18.61 |

捕获实际收到 26 个 complete frames；渲染阶段收到 23 个，完成 600 次渲染提交；均正常退出且无 stream error。静态桌面不要求每秒 30 个 complete frames，不能将少量完整帧当作黑屏故障。仅捕获与捕获+渲染的 ColorSync 日志频率和邻近空持有窗口相近，**没有观察到它们独立加剧 ColorSync 循环的明显证据**；未测完整 GUI、GPU 和交互延迟，不能排除其他预览性能问题。首次接入后 colorsyncd 的较高 CPU 包含配置生成/重配置的短期影响，不能当成长期稳态值。

所有 held/removed 性能窗口中，开始/结束拓扑一致。四次创建及四次移除重复呈现在线三屏负载较高、离线两屏下降的模式，支持“在线虚拟屏放大已有异常循环成本”。同身份重建也放大循环，说明避免生成新 ICC 并不能独自消除热插拔/在线显示成本。

后续移除窗口的频率从 15.44 上升到 18.82，存在时间趋势。实验顺序固定、无干净基线且只三个身份，不能据此判定增长由新增三个 ICC 导致；也没有证据声称 142 个小文件足以直接拖慢桌面。

全部移除后追加 60 秒恢复观察，频率仍为 18.61，profile 数保持 145，没有 OCU 虚拟屏或 VirtualDisplayHost 进程在线。说明至少这段时间内循环没有自行消退，仍不构成历史配置引发循环的完整因果证明。

## 查询对照与无效窗口

较早的 observe run 中，CG 查询目标 20 Hz，实际 292 次/20 秒；ColorSync 调用/s 为 13.56，邻近恢复为 13.40。SCK 枚举目标 2 Hz，实际 28 次；调用/s 为 13.41，前一恢复为 13.40。没有观察到查询频率升高带来对应的日志频率变化。这些是已有循环下的增量观察，不能证明查询在健康系统永远无影响。

该 run 的 CG 2 Hz 阶段，主线程移除了既有虚拟屏，拓扑变化，窗口不作为单变量证据。之后原缓存 display ID 失效，首次捕获失败，立即结束该 run；那次失败不作为捕获性能结论。demo 已改为每次捕获前重新查询在线目标；有效捕获数据来自上表 demo 自己持有的显示器。

## 还缺什么证据

目前可直接复现的是 **身份变化→新增持久 ICC** 和 **虚拟屏在线→已有循环处理范围/负载扩大**。还不能证明最初是谁启动了循环，也不能区分持久色彩/布局状态、物理链路与系统服务内部故障。

- root ColorSync/WindowServer 进程的堆栈采样被系统权限拒绝，没有自动提权。需要授权的堆栈证据才能区分上游重复请求与服务内部自循环。
- 需要健康基线或另一测试账户/设备，保留完整状态，再比较固定身份和变化身份。受控恢复历史状态是另一个实验，需要明确授权；不能靠删除所有色彩配置来“验证”。
- 当前无物理屏断开后的受控 baseline；用户此前拔掉 LG 仍卡是线索，不能代替同窗口指标。也没有从健康环境跑到 142 个文件的长循环复现。
- 显示器复用和固定身份池分别减少热插拔、无界身份增长，方向与证据一致；它们是预防/减轻措施，不等于已经修复系统里现存的循环。

外部项目的 [MirageKit 卡顿记录](https://github.com/EthanLipnik/MirageKit/blob/main/If-Your-Computer-Feels-Stuttery.md) 和 [AR Workspace Manager 的 ColorSync 调查](https://github.com/dripster82/ar_workspace_manager_for_xreal/blob/main/Docs/ColorSync-AirII-investigation.md) 提供相似线索。后者也记录了干净 registry 下依旧循环的案例，所以配置数量不能作为唯一解释。项目特定报告不替代本机堆栈或干净基线验证。
