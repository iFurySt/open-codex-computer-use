# 当前分支同构建：内置屏与 LG 条件各 30 次

日期：2026-10-06，macOS 26.5.1 / arm64。用户要求排除旧制品及外屏链路的混淆：先不接外屏测试 30 次，再接回 LG 测试 30 次。

## 结果

**同一份当前分支 helper/bridge 二进制，在内置屏条件没有复现 ColorSync 累积；LG 连接条件再次逐组累积，并在停止热插拔后持续高负载。当前真实创建/释放核心尚未解决这个条件下的问题，显示器复用属于减少触发的缓解策略。**

## 构建与变量

- `swift build` 使用独立全新 scratch 目录编译当前分支的 `apps/VirtualDisplayHost` 和 `packages/VirtualDisplayBridge`，不是直接复用之前 Dev 制品。构建源码 HEAD、每个源文件 SHA-256、签名后二进制 SHA-256 已记录在脱敏指标；两个条件完全相同。使用既有 OCU Developer ID / hardened runtime，严格签名验证通过。
- 只测试生产显示器创建/释放核心，不把结果等同于整个最新 GUI、session registry 或默认 retain/reuse 行为的端到端测试。真正热插拔每个条件发生 30 次；正常默认保留/复用并不发生这些热插拔。
- 相同固定预热身份槽 28、1920×1080、1×，十组各三次，每次持有约 4 秒；两段 30 秒无热插拔基线、每组三次后 30 秒检查点、最后三段 30 秒被动窗口。同一种探针/采样方式。
- 60 次均验证自己的显示器从 CG 在线列表消失、helper 正常退出，清理错误为零；每个条件所有边界的物理屏身份/主屏/坐标稳定。146 份匹配的 OCU ICC 在所有批次和测量边界数量及 SHA-256 不变。
- 没有 SCK/Metal/AX/input 测试负载，没有删除 ICC、重启 ColorSync 或主 App，也没有修改 Dock/Spaces/色彩偏好。既有后台 runtime 未全部关闭，因此不能宣称不存在任何其他显示消费者。没有识别系统内部 XPC 发起者。

## 根因能说到哪一层

**直接耗 CPU 的工作已明确：ColorSync 在频繁重复接收显示信息请求，并重复处理物理屏 profile。** LG 条件从约 0.20 请求/秒升至约 12 请求/秒，同时服务 CPU 从约 1.5% 增至约 78%；ICC 不变，不能将日志里的 profile 创建函数名误读成每次都写一个新文件。

**触发组合已获得两条件对照支持：当前显示器核心的反复热插拔，叠加这台机器的外屏连接/显示拓扑条件。** 内置屏 30 次不累积，外屏连接基线正常，热插拔后逐组累积。因此既不能声称“肯定是 LG/扩展坞自行故障，与 OCU 无关”，也不能声称“任何设备上 OCU 单独都会使 ColorSync 累积”。在这个组合上，OCU 的创建/销毁是可重复触发操作，应视为未解决的兼容性问题。

**系统内部具体缺陷尚未定位。** 可能的重配置注册/回调/重试未收敛只是待验证机制，不作为已确认泄漏点。LG、CalDigit/连接路径、线缆、主屏/排列及系统显示状态在连接切换中没有逐项分离。也未随机化试验顺序或控制所有后台消费者，不能直接给硬件定责，不能宣称内部一定是 ColorSync 或 WindowServer 哪一处缺陷。

此前断开/接回对照表明同样的 ICC 文件仍可健康运行；本次进一步确认固定身份并不能单独解决外屏条件下的持续工作。优先保持显示器、复用会话，减少真实热插拔；不能把这个缓解称为已修根因。下一层隔离可在恢复健康后比较 LG 直连/原扩展坞链路，以及 helper-only 与关闭其他显示消费者的条件，再考虑最小化显示配置事务；这些尚未执行，不自动增加本次压力测试次数。
