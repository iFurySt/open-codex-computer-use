# Display hotplug and physical disconnect recovery

- Request: reproduce persistent ColorSync load after virtual-screen creation/removal and test whether unplugging/replugging LG resolves it.
- Design: passive connected baseline; at most two batches of three warm fixed-identity create/remove cycles, each bracketed by passive recovery. Stop hotplug on sustained abnormal load. Then user-controlled physical disconnect, wait for a stable built-in-only window, reconnect and observe.
- Boundary: no ICC deletion, ColorSync restart, main App termination, random serial or unrelated helper cleanup. Abort hotplug if another OCU virtual screen is online. No new virtual screen until current topology and user availability are confirmed. Raw device identifiers stay local.
- Evidence: CPU deltas, display-information XPC request rate, online CG topology/helper absence, ICC count/hash, user typing/dragging observations. Healthy-to-fault reproduction must be distinguished from an already-abnormal baseline. Disconnect changes topology as well as service state, so recovery alone does not prove ICC residue caused the fault.
- Status: complete. Six bounded warm cycles verified removed, with 146 ICC hashes unchanged. Healthy connected baseline 1.50% ColorSync CPU / 0.196 XPC/s; persistent removed-state windows 17.53–17.99% / 2.525–2.581; disconnected stable window 0 / 0; reconnect windows 1.32–1.57% / 0.198–0.219. Service PIDs and restored physical topology unchanged. User reports smooth after reconnect. Historical severe stutter and internal caller remain unproven.
- Evidence: [report](../../references/20261006-display-disconnect-recovery.md), [sanitized metrics](../../../experiments/DisplayPerformance/results-recovery-20261006.json). Four offline metric tests passed; no production code/bundle change or App restart.
