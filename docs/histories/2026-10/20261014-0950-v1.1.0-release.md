## 用户诉求

PR #92 合并后，从 main 发布 v1.1.0。

## 发布准备

- 当前任务 checkout 切至合并后的 main，保留其他会话 checkout。
- 补齐 Locked Use native / arm64 / x86_64 / universal 组件构建，按同一签名 team 嵌入主 App。正式签名构建默认包含组件；CI 强制嵌入，缺少签名时拒绝不完整发布。
- 新增只读 bundle 检查：四个运行组件、架构与主 App 一致、签名 ID / team、严格嵌套签名；npm staging 与直接下载归档均执行检查。组件 plist 版本读取公共 manifest，避免继续发布开发占位版本。
- 同步发布指南与中英文使用说明。准备与版本 bump 分开提交。

## 发布状态

本地 release-package 全流程完成，三个 tgz、直接下载归档、skill 与校验和均已生成；准备提交与版本 bump 分开，接下来推 main / v1.1.0 并检查 CI 公证、npm 与 GitHub Release。

首次 CI 的 metadata 和 DMG job 成功，npm job 在组件签名阶段找不到临时 keychain 中的 identity，未进入 npm / GitHub 发布。组件签名 helper 现在与原主 App 一样临时加入签名 keychain 并恢复原搜索列表；模拟 CI keychain 的成功 / 失败路径回归通过，不修改本机真实 keychain。修复后更新尚未发布的 v1.1.0 tag 并重跑。

修正搜索列表后 CI 完成组件签名与插件 ABI，随后 kernel verifier 正例被拒绝；本机同一正负例仍通过。新增仅链接到构建诊断程序的逐项 requirement 位图与签名用途输出，定位 CI 分类 / 标志差异；生产插件 verifier 不变。诊断运行不发布 npm 或 GitHub Release，待查明后再更新 tag。

CI 诊断确认 Developer ID 分类、team、运行时均通过，仅 CS_REQUIRE_LV 缺失（failedChecks=64）。主 App 与 Locked Use 组件签名显式使用 runtime,library，避免不同宿主环境对隐式 library validation 的差异；不放宽生产进程 requirement。
